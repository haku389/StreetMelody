# メロディコード・ソーシャル設計（フォロー / フレンド / ベストフレンド / メロディミックス）

本書は「すれちがい起点のフォロー型ソーシャル」「実ユーザー・プロフィール基盤」「メロディコードとメロディミックスによるベストフレンド成立」の設計をまとめたもの。実装前の“設計を固める”ためのドキュメント。関連: [implementation-log.md](implementation-log.md) の M-8/M-9（フレンド共有・フォロー型の現状）。

---

## 1. ビジョン / 全体像

- ユーザーは登録・ログイン後、**プロフィール**（ユーザーID・誕生日・性別・自己紹介・お気に入り曲・**メロディ**）を設定する。
- 出会いは **すれちがい（近接通信）** 起点。出会った“実ユーザー”を**フォロー**できる（SNS型）。
- **相互フォロー＝フレンド**。
- **ベストフレンド**は、フレンドの中から特別な儀式で成立：
  - **対面**：近接で端末同士がつながり相手情報を表示 → **「メロディミックス」ボタン**で自分と相手のメロディが混ざって再生される → ベスト成立。
  - **遠隔**：自分のメロディに基づく**メロディコード**を交換してベスト成立。
- 公開範囲（今聴いてる曲などの共有）は **オフ / ベストフレンド / フレンド / 全体公開** の4段階（実装済みの土台あり）。

---

## 2. 関係モデル（用語の定義）

| 状態 | 定義 | データ |
|---|---|---|
| フォロー | A→B の一方向 | `follows(follower=A, followee=B)` |
| フレンド | 相互フォロー（A⇄B） | `follows` 両方向が存在 |
| ベストフレンド | フレンドのうち、儀式で相互確定した特別な関係（相互・確定制） | 後述（`best_friend_links` 推奨） |

- ベストは**相互かつ確定操作（メロディミックス or コード交換）**で成立させる（＝勝手に付けられない）。
- 既存の `follows.is_best`（M-9）は「片側フラグ」だったが、本設計では**相互確定のベスト**に格上げするため、確定リンクを別管理にするのが綺麗（§7）。

## 3. ユーザー基盤（アカウント・プロフィール・オンボーディング）

### 3.1 認証
- 既存の Supabase OAuth（Apple / Google / Spotify / メール）を流用。匿名から昇格も可。
- 初回ログイン後に**オンボーディング（プロフィール設定）**へ誘導。

### 3.2 プロフィール項目
- **ユーザーID（handle）**：英数の一意ハンドル（例 `@haku_melo`）。**全体で一意**＝遠隔フォロー/検索や安定識別の鍵。
- 表示名（display_name）★必須公開
- 自己紹介（bio）★必須公開
- **好きなアーティスト**（favorite_artist_ids：複数）★必須公開
- お気に入り曲（favorite_track_ids：複数）★必須公開
- 誕生日（birthday）／性別（gender, 任意・"その他/未回答"あり）→ 公開範囲をユーザーが設定
- **メロディ**（§4。初期は自動付与、将来は自作）
- アイコン（任意・将来）

### 3.3 プロフィール公開範囲【確定方針】
- **必ず公開（全員が見られる）**：表示名・自己紹介・好きなアーティスト・好きな曲。
- **ユーザーが公開範囲を設定できる**：上記以外（誕生日・性別・将来の項目など）。スコープは `公開 / フォロワー / フレンド / ベスト / 非公開` から項目ごと（またはグループごと）に選択。
- 実装：項目→スコープのマップ（`profile_visibility jsonb`）を持ち、他者プロフィール取得は **SECURITY DEFINER の RPC `get_profile(target)`** で「閲覧者との関係（フォロー/フレンド/ベスト）× 各項目のスコープ」を突き合わせて**フィルタ済みの行**を返す（RLS だけで項目別可視は煩雑なため RPC 方式を推奨）。必須公開項目は常に含める。

### 3.3 設定画面（最初の実装対象候補）
- ログイン → handle 入力（重複チェック）→ 誕生日/性別/bio/お気に入り曲 → メロディ確認（自動付与を試聴）→ 完了。
- 後から編集可能なプロフィール編集画面。

## 4. メロディコード（個々のユーザーのテーマ）

### 4.1 表現（データ）
- メロディ＝**音符列**。例：`[{deg, oct, start, dur}, ...]`
  - `deg`：スケール内の度数（ペンタトニックなら 0–4）
  - `oct`：オクターブ（基準±1程度）
  - `start`/`dur`：グリッド上の開始/長さ（16分音符単位など）
- 長さ：**約4秒**（例：120BPMで2小節＝8拍）。
- 保存：profiles に JSON（`melody jsonb`）。`melody_seed`（user_id ハッシュ）を持たせ再現/検証可能に。

### 4.2 付与（初期：自動生成）
- 登録時に**自動生成**（後から自作機能を追加予定）。
- 生成ルール（心地よさのため）：
  - **メジャー・ペンタトニック**内のみ（§5の理由）。
  - 跳躍を抑える（隣接度数中心、たまに3度跳躍）。
  - **終止は主音（deg0）に着地**して“締まり”を出す。
  - リズムはグリッドにクオンタイズ（無音休符も可）。
  - シード＝user_id 由来＝「その人固有・再現可能」。

### 4.3 メロディコード（遠隔ベスト用の文字列）
- 音符列（度数列）を短い文字列にエンコード。
  - 例：8音をペンタ度数（0–4）＋オクターブで base-32 化 → 数文字。
  - 表示は **ドレミ表記**（例 `ソミミ-ファレレド`）や **5音絵文字**（🔵🟢🟡🟠🔴）でも可（“話題・自慢”になる見せ方）。
- **一意化**：メロディは衝突しうるので、コード単体で人を引くには **handle と併用** か、コードに**短い一意サフィックス**を付ける（例 `ソミミファ-7Q`）。遠隔追加の本人特定は **handle が主キー**、メロディコードは“フレーバー＋本人確認の合言葉”という位置づけが安全。

## 5. メロディミックス（音楽設計：ここが肝）

目的：**任意の2人のメロディを混ぜても必ず心地よく響く**こと。そのために“混ざっても濁らない”制約を最初から敷く。

### 5.1 必ず良い響きにするための制約
- **共通スケール＝メジャー・ペンタトニック**（例 Cメジャーペンタ: C D E G A）。
  - ペンタは構成音同士が半音衝突しにくく、**どの音を重ねても濁りにくい** → 2メロディ同時再生の安全性を担保する核。
- **共通キー固定**（全ユーザー同一キー。例 C）。実装が単純。将来は移調で“相手のキーに合わせる”拡張も可。
- **共通テンポ＆尺**（例 100–120BPM・2小節）。グリッド（16分）にクオンタイズして拍が揃う。
- **音域の住み分け**：自分は基準オクターブ、相手は+1（or 音色を分ける）。聞き分け＆濁り回避。

**初期値【確定・ただし変更前提】**：`Cメジャーペンタトニック / 110BPM / 2小節（約4.4秒） / 16分グリッド`。
- 後で変更できるよう、**メロディは自身のメタデータ（scale, key, tempo, bars, grid）を一緒に保存**する（`melody.meta`）。グローバル既定を将来変えても、旧メロディは自分のメタで正しく再生・ミックスできる。
- 異なるキー/テンポのメロディを混ぜる場合は**ミックス時に共通基準へ正規化（移調・テンポ合わせ）**してから重ねる方針（初期は全員同一基準なので不要）。

### 5.2 ミックス方式（段階的に選択可）
- **A. レイヤー（同時再生・対位法的）**【初期推奨】：2メロディを同時に重ねる。ペンタ＋音域/音色住み分けで常に成立。最も“ミックス感”がある。
- **B. コール＆レスポンス**：1小節ずつ交互。各自のメロディが立ち、わかりやすい。
- **C. ハーモナイズ**：一方をリード、他方から3度/6度のハモり or ベースを生成。
- **初期実装は A（レイヤー）＋ペンタ固定＋音域住み分け**。破綻せず一番手軽。

### 5.3 再生技術（iOS）
- `AVAudioEngine` ＋ `AVAudioUnitSampler`（or 簡易シンセ）。
- 2メロディを2プレイヤー/2トラックで**同一タイムライン上にスケジュール**（テンポ同期）。
- 音色：自分＝マリンバ系、相手＝ベル/ピアノ系などで分離。
- ミックス結果は**その場で生成・再生**（録音/共有は将来オプション）。

### 5.4 “2人の証”としての演出
- ミックス完成時に**ペア固有のミックス**が生まれる＝ベスト成立の記念。
- 将来：ミックスを保存してベストフレンドのプロフィールに“2人のテーマ”として表示。

## 6. ベストフレンド成立フロー

### 6.1 対面（近接）
1. 近接でつながり相手プロフィール（メロディ含む）を表示。
2. **「メロディミックス」**ボタン → 自分＋相手のメロディが混ざって再生。
3. 双方が合意 → **相互ベスト成立**。

### 6.2 遠隔
- **メロディコード**（§4.3）を相手に伝え、相手が入力（or 自分が相手のコードを入力）→ 双方確定で相互ベスト成立。
- handle ＋ メロディコードの組み合わせで本人特定の安全性を確保。

### 6.3 近接アーキテクチャ：トリガー層 × 通信層の分離【確定】

採用方針：**「トリガー（IDの受け渡し）」と「実データ通信」を分離**する。トリガーで相手の handle / 一時接続トークンを受け取り、その情報をもとに **MultipeerConnectivity（対面P2P）** または **サーバー（Supabase）** で本通信する。

- **トリガー層（相手特定）**：相手の handle ＋ 短命の接続トークン（例 `streetmelody://connect?u=<handle>&t=<token>`）を受け渡す。
  - **QRコード**＝iPhone間の標準トリガー（片方表示・片方スキャン）。← **現状の主トリガー**。
  - **NFCタグ（物理）**＝同じURL/IDを書いたタグを“かざして読む”。イベント設置・名刺ステッカー等で同一フローに乗る。← **将来オプション**。
  - ⚠️ 技術前提：**iPhone 同士の NFC P2P は公開APIで不可**（Core NFC は主にタグ読取・端末をタグとして読ませる card emulation は第三者アプリ不可）。よって「iPhone2台をかざして直接交換」はNFCでは不可。**iPhone間のトリガーは実質QR**。NFCは“物理タグ”用途で同一アーキテクチャに後付け可能（トリガー層を抽象化しておく）。
- **通信層（本データ交換）**：
  - **MultipeerConnectivity**（Wi‑Fi/BLE P2P）：対面でその場の**メロディミックス共演**・ベスト確定ハンドシェイク。
  - **サーバー（Supabase）**：遠隔・非同期や確定レコードの保存。両者合意の記録（§7.3）。
- **出会い（フォロー供給源）**：既存の **BLEすれちがい** で user_id を交換し“出会い”を記録 → フォロー候補に。
- まとめ：**出会い＝BLEすれちがい / 対面ベスト＝QRトリガー＋MultipeerConnectivityでミックス共演＋サーバーに相互確定 / 遠隔ベスト＝メロディコード＋サーバー / NFCタグは将来の物理トリガー**。トリガー層は `ConnectTrigger`（QR実装・NFC実装を差し替え可能）として抽象化する。

## 7. データモデル（案）

### 7.1 profiles 拡張（既存 public.profiles を拡張 or 新カラム）
```
profiles(
  user_id uuid pk,
  handle text unique,            -- @英数ハンドル（一意）
  display_name text,             -- ★必須公開
  bio text,                      -- ★必須公開
  favorite_artist_ids text[],    -- ★必須公開（好きなアーティスト）
  favorite_track_ids text[],     -- ★必須公開（好きな曲）
  birthday date,                 -- 公開範囲は設定に従う
  gender text,                   -- 'male'|'female'|'other'|'na'、公開範囲は設定に従う
  melody jsonb,                  -- 音符列＋meta(scale,key,tempo,bars,grid)
  melody_seed text,
  profile_visibility jsonb,      -- 項目→スコープ('public'|'followers'|'friends'|'best'|'private')
  ...既存(level, coins 等)
)
```
- RLS：本人は自分の行を update。**他者プロフィールの閲覧**は **RPC `get_profile(target)`（SECURITY DEFINER）** で関係×公開設定をフィルタして返す（§3.3）。必須公開4項目は常に返す。
- handle 重複チェック：`check_handle_available(handle)` RPC（存在可否のみ返す）。

### 7.2 follows（既存・M-9）
```
follows(follower_id, followee_id, nickname, is_best, created_at)
```
- フォロー/フレンド（相互）は既存のまま使える。

### 7.3 best_friend_links（新規・相互確定のベスト）
```
best_friend_links(
  user_low uuid, user_high uuid,     -- 正規化（low<high）で1ペア1行
  created_at timestamptz,
  method text,                       -- 'mix'(対面) | 'code'(遠隔)
  primary key(user_low, user_high)
)
```
- ベストは**相互確定**なので follows.is_best ではなくこの1ペア1行で持つと整合的。
- now_playing の `bestfriends` 可視性 RLS は「閲覧者と所有者が best_friend_links に存在するか」で判定（双方向で対称）。
- 確定フロー：対面/遠隔の合意 → サーバ関数 or 双方の同意レコードで link を作成（成りすまし防止に**両者の合意**が要る点に注意）。

### 7.4 既存 now_playing 可視性との接続
- `bestfriends` 行の RLS を best_friend_links ベースへ更新（現状は follows.is_best 片側判定）。

## 8. 段階的実装計画（フェーズ）

- **P0（設計）**：本書。← 今ここ
- **P1 プロフィール基盤**：profiles 拡張＋オンボーディング/編集画面（handle 一意・誕生日・性別・bio・お気に入り曲）。メロディ自動付与＋**メロディ再生**（単体）。
- **P2 メロディミックス（音楽コア）**：2メロディのレイヤー再生（ペンタ固定・音域住み分け）。まずは自分＋ダミーで成立確認 → 2ユーザー。
- **P3 すれちがいの実ユーザー連動**：BLE で user_id 交換 → 出会い記録 → フォロー導線。
- **P4 ベスト成立**：対面（QR/Multipeer＋ミックス）/遠隔（メロディコード）→ best_friend_links → 可視性 `bestfriends` 接続。
- **P5 仕上げ**：プロフィール閲覧・通知・ミックス保存 等。

## 9. 決定事項 / 残課題

**決定済み**
- ✅ 近接アーキテクチャ（§6.3）：**トリガー（QR、将来NFCタグ）× 通信（MultipeerConnectivity / サーバー）の分離**。iPhone間トリガーは **QR で確定**。出会いは BLEすれちがい。
  - 補足（NFC/HCE 不可の結論）：iOS では第三者アプリ向けの汎用カードエミュレーション(HCE)が無く、HCEは iOS17.4+ の特別エンタイトルメント（商用・地域限定・審査制）でのみ。`NFCISO7816APDU` はリーダー側APIでエミュレーションには使えない。さらに Core NFC 読み取り自体が**有料 Apple Developer Program 必須**（無料個人Teamでは不可）。→ **QR（カメラのみ・エンタイトルメント不要・無料Teamで可）を採用**。NFC物理タグ/HCEは有料Program加入後の将来オプション。
- ✅ メロディ初期パラメータ：**Cメジャーペンタ / 110BPM / 2小節（約4.4秒）**（変更前提・メロディに meta 同梱で前方互換）。
- ✅ メロディは初期=自動付与、将来=自作。
- ✅ ベストは**両者の合意レコードが揃って成立**（成りすまし防止）。
- ✅ プロフィール公開範囲：**ユーザーが項目ごとに設定可**。ただし**表示名・自己紹介・好きなアーティスト・好きな曲は必ず公開**。

**残課題（実装時に詰める）**
1. handle の命名規約（長さ・文字種・予約語・変更可否）。
2. メロディコードの最終フォーマット（ドレミ/絵文字/英数）と一意化（handle併用）。
3. ベスト相互確定の具体実装（合意レコード2件 or サーバRPC・対面トークンの有効期限）。
4. `get_profile` RPC の項目別フィルタ仕様の確定。
5. すれちがい（BLE）に載せる payload と出会い→フォロー導線の UX。
